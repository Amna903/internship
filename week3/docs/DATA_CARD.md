# Data card: synthetic appointment no-shows

## Provenance and license

- **Source:** generated by this repository (`backend/ml/data.py`, `generate()`), seed `42`, 20,000 rows,
  7,000 fictional patient ids. No real dataset, record or person was used or sampled.
- **Why synthetic, not a public dataset:** the brief prefers synthetic data. Public no-show datasets are
  real (if de-identified) patient records. A generator also tells us the *true* probability behind every
  row, which lets us measure the best score any model could reach (the "oracle ceiling").
- **License:** same as the repository code. It is ours to share: no third-party terms.
- **Reproduce:** `python -m ml.train` writes `backend/ml/data/appointments_synthetic.csv` (git-ignored).
  SHA-256 of the file is recorded in `ml/artifacts/no-show-1.0.0.json` (`data.sha256`) and checked by a test.

## Schema

| Column | Type | Range / values | Role |
|---|---|---|---|
| `appointment_id` | int | 1…20000 | identifier, **not a feature** |
| `patient_ref` | str | `P00001`… | identifier, **not a feature**; used to group the split |
| `lead_time_days` | int | 0–180 | feature |
| `appointment_weekday` | str | monday…saturday | feature |
| `appointment_hour` | int | 8–18 | feature |
| `age_band` | str | 18-24 … 65+ | feature (see bias) |
| `visit_type` | str | in_person, video, phone | feature |
| `booking_channel` | str | web, phone, app | feature |
| `reminder_sent` | bool | | feature |
| `prior_appointments` | int | 0–13 observed | feature |
| `prior_no_shows` | int | ≤ prior_appointments | feature |
| `distance_km` | float | 0.4–203, **~10% missing** | feature (imputed) |
| `checked_in` | bool | | **LEAKAGE, never a feature**: recorded after the visit, equals `not no_show` |
| `no_show` | 0/1 | 16.4% positive | **target** |

## How rows are generated

Each row's log-odds of a no-show is a sum of planted effects (`ml/data.py`): longer lead time ↑,
reminder ↓, prior no-show *rate* ↑↑, new patient ↑, younger age ↑, video/phone ↓, Monday/Friday ↑,
early/late hours ↑, distance ↑ (in-person only), and an interaction **long wait AND no reminder ↑**.
The outcome is a coin flip with that probability, so even a perfect model is far from certain.

## Limitations

- **The model can only learn our assumptions.** The effects above are invented to be plausible. Metrics
  say how well a model recovers *this generator*, not how no-shows behave in any real clinic.
- **Independence:** a patient's age is fixed, but other columns are drawn per appointment. Real
  patients have habits that carry across visits; ours mostly don't.
- **No time dimension:** no dates, seasons or trends, so there's no drift and no time-based split.
- **Missingness is random (MCAR) by construction.** Real missing data usually isn't.
- **Range:** `prior_appointments` never exceeds 13 here. The API accepts up to 200, but the model has
  never seen such values (trees and linear models extrapolate differently).

## Class imbalance

16.4% no-show (about 1 in 6). A model that always says "will attend" is ~83.6% accurate and useless, so:
accuracy is not reported; models are ranked by **PR-AUC** (focuses on the rare class) with ROC-AUC and
Brier score alongside; probabilities are left uncalibrated-by-reweighting (no `class_weight`), and the
"high" threshold is chosen on validation by best F1 instead.

## Bias

- **Age is a planted driver**, and the age mix is skewed young (8% are 65+). On the test set, people aged
  18–24 who *do* attend are flagged high-risk 29.5% of the time, versus 4.6% for 55–64 (see
  `ml/reports/metrics.md`). That is acceptable only for a **supportive** action (an extra reminder). The
  output must never be used to refuse, deprioritise or double-book someone; that would turn an age
  pattern into an age penalty. Dropping `age_band` is the obvious next experiment if any restrictive use
  were ever considered.
- **Reminder is confounded with outcome by design.** In real data, clinics often remind the people they
  already expect to miss, which would make reminders look harmful. This generator assumes reminders are random.
